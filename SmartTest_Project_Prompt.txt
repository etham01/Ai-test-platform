三、产品功能范围
======================================================================

必须实现的核心模块：

1.  项目管理

-   创建、查询、修改、删除项目
-   项目包含名称、描述、base_url、浏览器类型、采集参数和状态
-   项目之间的数据必须隔离，所有资源查询都必须校验 project_id 归属
-   第一版可以采用单用户或简化用户体系，但接口和数据模型应避免未来无法扩展
-   如果没有明确的认证需求，不要自行引入复杂
    OAuth；但应避免任何人通过猜测 ID 访问其他项目数据

2.  LLM 配置管理

-   配置 OpenAI 兼容 API 的 base_url、模型名、API Key
-   API Key 不返回给前端；前端只显示是否已配置或脱敏状态
-   密钥优先从环境变量或加密存储读取
-   支持测试连接功能，但不要把密钥写入日志
-   提供 .env.example，不提供真实密钥

3.  页面解析与多页面探索

-   用户输入起始 URL，后端 Playwright 访问目标站点
-   提取页面 URL、标题、页面文本摘要、DOM/可访问性信息和交互元素
-   交互元素至少覆盖常见 input、button、a、select、textarea、form 等
-   尽可能提取 role、accessible
    name、label、placeholder、文本、id、name、type、href 等属性
-   记录可用于 Playwright 的候选定位信息
-   发现页面之间的链接、表单提交或可观察跳转关系
-   用有限深度 BFS 或其他可解释策略探索站内页面
-   支持 max_pages、max_depth、超时和 URL 去重
-   默认限制在项目授权的 base_url
    同源范围内；对重定向后的域名也要重新校验
-   过滤 mailto、javascript、data、文件下载、logout
    等不适合自动跟随的链接
-   避免无限点击、重复提交表单和危险操作
-   需要登录的站点允许用户提供合法会话状态文件或人工完成登录；不得尝试绕过验证码、访问控制或认证机制
-   保存页面快照和结构化数据；控制 DOM 内容大小，敏感字段脱敏
-   对页面采集任务提供状态和进度

4.  页面关系与业务流程分析

-   将页面建模为节点，将观察到的跳转/交互建模为有向边
-   页面关系数据应标明来源和可信程度，例如
    observed_link、observed_navigation、model_inferred
-   将用户测试需求、页面结构摘要、页面关系交给 LLM
-   LLM 输出业务流程候选、涉及页面、步骤和不确定点
-   模型推断的业务规则必须标记为
    inferred/needs_confirmation，不可伪装成网站真实规则
-   支持用户查看并确认/编辑生成的业务流程
-   多页面流程必须考虑同一 Browser Context 的 Cookie/会话连续性

5.  测试需求管理

-   用户可以为项目创建、编辑和查看测试需求
-   需求可以关联一个或多个页面
-   保存原始需求文本和必要的生成配置
-   不要将用户未提供的业务预期擅自当作确定事实

6.  LLM 测试用例生成

-   按用户选择的生成方式：由 LLM 生成测试用例
-   输入包括用户需求、页面结构、页面关系、已确认业务流程和必要的项目上下文
-   输出为结构化 JSON，并使用 Pydantic 严格校验
-   测试用例建议字段：
    case_code、title、module、priority、preconditions、related_page_ids、steps、test_data、expected_result、assertions、assumptions、generation_model、created_at
-   每个 step 至少包含
    step_no、page_reference、action、target、value、description
-   assertion 包含 assertion_type、target、expected、source 或
    confidence
-   用例必须能追溯到需求和相关页面
-   对模型推断的预期结果明确标记为待确认，不得直接当作确定业务规则
-   对无效 JSON 或字段缺失进行有限次数修复/重试
-   生成后做结构校验、页面 ID 校验、步骤完整性校验和重复提示
-   不要声称自定义测试维度覆盖率等同代码覆盖率
-   保存 prompt
    版本、模型名、生成耗时和原始响应的安全摘要；避免保存不必要的敏感内容
-   支持用例查看、编辑、删除和重新生成

7.  LLM 自动化脚本生成

-   按用户选择：由 LLM 根据结构化用例、页面信息和项目上下文生成 Python
    Pytest + Playwright 脚本
-   使用明确 Prompt，要求只输出约定格式的脚本内容或结构化响应
-   每条用例生成独立可追踪的脚本，或采用合理的模块组织
-   脚本必须有明确的测试函数、必要 Fixture、断言和可诊断日志
-   优先使用 Playwright role/label/placeholder/text
    等语义定位；不稳定时才使用 CSS 等定位
-   多页面脚本要处理页面跳转和会话状态
-   不要假定页面元素一定存在；应使用等待和合理超时
-   脚本生成后必须做 Python AST 语法检查、依赖检查和安全策略检查
-   检查危险模块导入、危险函数、子进程、任意文件访问、网络访问、环境变量读取等风险
-   安全检查不能仅依赖黑名单；优先采用容器隔离、最小权限和网络限制
-   保存脚本版本、生成模型、生成时间和关联用例
-   支持预览、编辑、下载、重新生成
-   不要把 LLM 输出脚本当成可信代码

8.  自动化执行

-   用户选择脚本或用例后创建执行任务
-   执行器在独立工作目录运行 pytest
-   支持 Chromium/headless 第一版
-   配置运行超时、CPU/内存限制（容器可用时）、输出日志大小限制
-   对目标网站执行 SSRF 防护：禁止访问
    localhost、私有网段、链路本地、云元数据地址及未授权域名；DNS
    解析和重定向都要校验，防止 DNS rebinding
-   执行网络访问范围应受控，只允许用户授权的目标站点及明确允许的资源域名
-   不将 FastAPI 主进程的敏感环境变量暴露给测试脚本
-   不以 root 身份运行不可信测试代码
-   记录 pending/running/passed/failed/error/cancelled 状态
-   记录开始结束时间、总数、通过数、失败数、跳过数、错误信息、日志、截图、报告文件路径
-   取消任务应尽可能终止 Celery task 和底层子进程/容器
-   不允许多个任务覆盖彼此工作目录或报告文件

9.  结果分析与报告

-   解析 pytest 结果，逐条保存测试结果
-   使用 pytest-html 生成 HTML 报告
-   记录失败步骤、异常类型、traceback 摘要、截图和必要的浏览器信息
-   可调用 LLM 对失败日志进行分析，输出可能原因、证据、建议和置信度
-   明确区分“观察到的错误”和“模型推测原因”
-   失败分析不得自动修改生产数据或无条件重跑
-   前端展示执行统计、逐条结果、日志和报告入口

10. 前端体验

-   采用简洁、专业、适合毕业设计演示的管理平台界面
-   左侧导航，主要页面包括：项目概览、页面管理、业务流程、测试需求、测试用例、脚本管理、测试执行、测试报告、项目设置
-   提供加载、空状态、错误状态、任务进度和成功提示
-   关键操作有确认提示
-   长任务不能阻塞页面；可轮询任务状态，后续可升级 SSE
-   不要使用只有视觉效果但没有后端行为的按钮
-   API 类型和前端 TypeScript 类型保持一致

======================================================================
九、关键工程实现要求
======================================================================

1.  统一数据协议

-   使用 Pydantic
    定义页面模型、页面元素模型、业务流程模型、测试用例模型、测试步骤模型、脚本生成结果模型、任务状态模型。
-   前端 TypeScript 类型与后端 Schema 对齐。
-   LLM 输出先解析、校验，再进入业务数据库。

2.  LLM Prompt 设计

-   Prompt 采用独立文件或模板，不要散落在业务代码中。
-   对每个任务明确角色、输入结构、输出结构、约束和示例。
-   要求模型只依据提供的页面和需求，不确定内容列为 assumptions。
-   对预期结果标注来源：user_requirement、observed_page、model_inference。
-   生成脚本必须要求模型只使用 Playwright/Pytest
    允许的接口和提供的页面上下文。
-   对长页面上下文做摘要、裁剪和分块，避免无边界塞入整个 DOM。
-   记录模型名称、Prompt 版本、token/耗时（若 API 返回）和错误信息。

3.  多页面探索

-   URL 规范化时处理 fragment、默认端口、相对 URL、尾部斜杠等情况。
-   默认不跟随外域。
-   避免对表单进行真实提交或对页面进行不可逆操作，除非用户明确指定并确认。
-   不自动处理验证码或绕过登录。
-   页面采集和测试执行使用可配置的超时。
-   支持用户手动添加 URL。

4.  脚本安全

-   模型生成的脚本是潜在不可信代码。
-   AST 检查只是辅助，不是完整沙箱。
-   优先 Docker 非 root、只读根文件系统（必要目录除外）、限制
    CPU/内存/PID、限制运行时长、限制网络出口、不给宿主敏感目录和环境变量。
-   禁止把 API Key 和数据库凭据传给测试容器。
-   执行器只挂载本次任务工作目录。
-   对脚本文件名和路径做规范化，防止路径穿越。
-   日志和报告文件大小设置上限。
-   用户取消任务时尽量清理子进程/容器。

5.  网络安全

-   页面采集目标和脚本执行目标必须经过 URL allowlist 校验。
-   防 SSRF：拒绝
    localhost、私有地址、环回地址、链路本地、保留地址和云元数据地址。
-   DNS 解析后校验 IP；处理重定向并再次校验；避免 DNS rebinding。
-   生产部署不要默认开放任意网络访问。
-   开发测试可使用本地 fixture
    网站，但通过专门配置明确允许，不要把生产策略整体关闭。

6.  数据与隐私

-   日志脱敏，不记录 API Key、Cookie、Authorization
    Header、密码和敏感表单值。
-   DOM 采集时对 password、token、email 等敏感字段做合理处理。
-   项目删除采用明确策略，必要时软删除。
-   报告下载和文件读取校验项目归属。
-   上传文件限制类型、大小和路径。

7.  可维护性

-   使用类型标注。
-   重要业务逻辑写测试。
-   使用 Ruff 或等效工具进行 Python lint/format。
-   前端使用 ESLint/Prettier 或项目已有工具。
-   不要无理由引入过多依赖。
-   不要留下大量 pass、TODO、NotImplemented 或假实现。
-   对无法完成的点在 docs/KNOWN_LIMITATIONS.md 中说明。

十、测试网站与验证策略
======================================================================

不要依赖公网网站作为唯一测试环境。请创建一个本地示例 Web
测试站点，至少包含： - 首页 - 登录页 - 商品列表页 - 商品详情页 -
购物车页 - 订单确认页或一个简化业务完成页

本地站点应提供可重复的测试数据和明确的测试预期，便于验证多页面流程。
可以将其作为开发 fixture 或 demo app，与正式平台前后端分开。
如果实现成本过高，至少先实现首页、登录页、列表页和详情页，并在文档中说明范围。

端到端验证至少覆盖： 1. 创建项目。 2. 配置 LLM（无密钥时明确使用 mock
测试）。 3. 采集本地 demo 站点多个页面。 4. 查看页面元素与页面关系。 5.
创建测试需求。 6. 调用 LLM 或 mock provider 生成结构化用例。 7. 生成
Pytest + Playwright 脚本。 8. 语法/安全校验。 9.
执行一个成功用例和一个预期失败用例。 10. 保存执行结果和 HTML 报告。 11.
查看失败分析。 12. 重启服务后确认 MySQL 中的数据仍然存在。

对于没有真实 API Key 的环境： - 实现可替换的
MockLLMProvider，仅用于自动化测试和开发演示。 - UI
必须清楚显示当前使用真实模型还是 Mock。 - 不得把 Mock 生成结果描述成真实
LLM 生成效果。 - 真实 LLM 集成必须保留可用实现和配置说明。

十一、交互和执行规则
======================================================================

开始工作后按以下节奏执行：

第一步：检查环境与仓库。 第二步：给出精炼但充分的架构决策和风险清单。
第三步：把详细方案写入 docs 文档。 第四步：列出分阶段任务和验收条件。
第五步：开始实际实施，不要等待用户再次说“开始”。
第六步：每完成一个阶段，运行相关检查和测试。
第七步：遇到错误先自行诊断和修复；若属于外部凭据、权限或用户决策问题，再向用户提出一个具体问题。
第八步：持续更新实施计划中的完成状态。
第九步：最终进行端到端验证并编写交付说明。

每个阶段结束时，在回复中简要说明： - 本阶段完成了什么 -
创建/修改了哪些关键文件 - 运行了哪些命令 - 测试结果是什么 -
尚存问题是什么 - 下一阶段将做什么

不要每改一个文件就停下来询问。只有以下情况必须询问用户： -
将删除或覆盖已有重要数据/文件 - 需要用户提供真实 API
Key、网站账号或认证状态 - 需要付费服务或会产生费用 -
需要访问未明确授权的网站 -
存在多个会显著改变产品方向的方案且无法合理默认

如工具支持并且用户已授权，可自行运行安全的本地命令。安装依赖前检查项目现有环境和锁文件，优先使用项目既有包管理方式。
